# qBitX desktop feature parity audit

This checklist compares the native macOS preview with the desktop workflows in this qBittorrent source tree. “Present” means the main workflow is available in qBitX; “Partial” records a known limitation or a smaller workflow that still needs review. The Web API cannot expose every internal Qt behavior, so a native screen alone does not establish exact parity.

| Original desktop workflow | qBitX status | Current coverage and remaining work |

| Add torrent file, magnet, or URL | Present | The add-options window can preview metadata (size, date, comment, and hashes), select or skip all files, set per-file priorities and names, save location and incomplete path, category/tags, torrent rename, queue position, seed mode, stop condition, content layout, sequential/first-last priority, speed limits, and stopped/automatic management options. Its file filter supports plain text, wildcards, and regular expressions. Multiple `.torrent` files can be selected together and pass through the add flow one at a time. Save locations have recent history and a remembered last path; both bundled and remote backends provide folder browsing and free-space information from the machine running qBittorrent. The native “Show torrent addition options” preference controls file, link, clipboard, and Search additions; when off, qBitX applies the qBittorrent server defaults. With add options enabled, metadata-backed duplicate hashes show qBittorrent's tracker-merge confirmation; accepting adds missing tracker tiers and web seeds, declining leaves the existing torrent untouched, and private torrents show the no-merge warning. The confirmation preference is configurable and uses the server's merge setting as its default button. qBitX can preserve local `.torrent` sources, delete them after the server confirms an add, or also delete them when the add is cancelled; each add sheet can keep its source file, and qBitX preserves a source that changed after it was opened. qBitX can register for `.torrent` files and magnet links as macOS defaults, and routes opened items into the same add flow. For the bundled local library, qBitX also prompts to add `.torrent` files found inside a completed torrent. A remote server may not implement the metadata-preview API, and remote files cannot be opened in Mac apps. |

## Verification completed

The peer-log endpoint returned HTTP 200 with the expected JSON array from a disposable loopback backend.
- `swift test --scratch-path /tmp/qbitx-rss-css-tests` passed all 45 focused test cases, including RSS article markup safety, BBCode conversion, bounded inline styling, relative image/link handling, RSS downloader rule validation and RFC 2822 last-match parsing, and strict Web API version comparison for supported, older, missing, and malformed versions. The default workspace build path can fail macOS test-bundle signing when Finder metadata is present.
- The Add Torrent Links sheet preloads supported links from the clipboard, accepts newline-separated URLs, magnet links, and v1/v2 info hashes, removes duplicates, and routes each link through the existing add-options flow. Four focused parser tests cover accepted inputs, clipboard filtering, duplicates, hash conversion, and invalid lines.
- Packaged UI smoke test against a fresh `/tmp` backend profile and separate port; the current release executable launched, connected to qBittorrent v5.3.0beta1, and enabled peer-country resolution in that test profile. The profile and backend were isolated from the normal library.

## Backend API version support

- Full parity requires Web API 2.16.2 or newer, matching this source tree's `API_VERSION`. The 2.16.2 changelog adds RSS rule import/export and category share-limit fields used by qBitX.
- Torrent metadata preview requires Web API 2.11.9; using a search plugin to preview and add a result requires 2.13.1.
- qBitX reads the connected Web API version and warns when it is below the full-parity floor. Older servers may connect, but individual newer workflows can be unavailable.
